# Service Level Objective（服务级别目标 · SLO）

> 学科：AI Infrastructure · 专题：可靠性与可观测性 · 服务边界、窗口和用户可见性必须明确

## 1. 核心定义

服务级别目标（Service Level Objective，SLO）是在明确时间窗口内，对用户可感知服务表现制定的可测量数值目标。例如“滚动 28 天内至少 99.9% 的合格请求返回成功且端到端耗时低于 2s”。SLO 以具体的 SLI 为基础，应明确请求范围、时间窗、错误判定与是否按地区/模型拆分；它不等同对外具有合同效力的 SLA。

## 2. 形象理解

像给快递服务设目标：28 天内 99.9% 的包裹在约定期限内送达。真实到达率是 SLI，目标百分比是 SLO，若未达成要赔偿客户的合同条款才是 SLA。

## 3. 技术原理与核心内容

基于请求的 SLO 常设 `good_events/eligible_events ≥ target`；错误预算比例为 `1−target`，在同一统计窗口内允许失败事件数 `budget=(1−target)×eligible_events`。时间型 SLO 可按合格时间片测量，不能与按请求计数的定义混用。Burn rate 表示实际坏事件消耗速率相对允许预算速率，多窗口 burn-rate alert 帮助区分短期严重故障与长期偏差。SLO 应反映真实体验，而非“CPU usage < 80%”这种内部效率目标。

## 4. 工程实践与设计权衡

LLM 在线服务可区分完整响应成功率、TTFT 门限、TPOT/ITL 尾部与输出质量的 SLI；明确取消、客户端超时、HTTP 429、重试和流式中断是否进入分母。采用 rolling 28d 与短期告警窗口，按优先等级、付费层和地区审视；当预算快速消耗时暂停高风险发布、恢复健康，而不是单纯追求 100% SLO。

## 5. 易混概念与边界

SLI 是客观测量定义，SLO 是目标阈值，SLA 是面向服务消费者的协议与违约后果。SLO 的 99.9% 成功率不能直接等同 28 天的精确停机分钟数，除非采用时间型 SLI 并声明全天观察窗。

## 6. 中等难度面试题（含参考答案）

1. **问：为什么只用 GPU utilization 作为生成服务 SLO 不合适？** 答：它不能直接说明用户是否按时得到正确响应；服务可能 GPU 100% 但排队严重。应选择用户可感知的成功率/延迟 SLI，并让 GPU utilization 做诊断指标。

2. **问：同一个服务为什么可能设置多个 SLO？** 答：不同的体验维度如成功率、首 token 延迟、完成时延和数据新鲜度无法由单个指标覆盖。需为每项清晰定义分母、阈值与窗口。

## 7. 中等难度考试题（含解析）

1. **题：28 天有 200 万合格请求，SLO=99.9%，允许多少个坏事件？** 解：`2,000,000×0.001=**2,000 个**`；若实际坏事件 2,400 个，超出预算 400。

2. **题：28 天错误预算为 1,000 个事件，已发生 650 个坏事件，预算使用率与剩余量？** 解：`650/1000=**65%**` 已消耗；还剩 **350 个**坏事件额度。
