# Chaos Engineering（混沌工程）

> 学科：AI Infrastructure · 专题：可靠性与可观测性 · 具体告警、性能或会计口径需按环境与约定核对

## 1. 核心定义

混沌工程（Chaos Engineering）是在明确假设、可控范围与安全停止条件下，对系统注入故障或扰动，观察真实运行行为并验证系统韧性的工程方法。核心不是随机断电或制造事故，而是以正常稳态指标为参照，对网络分区、节点故障、存储超时、进程退出和依赖降级进行可重复实验。

## 2. 形象理解

像消防演习：在不危及生命的条件下模拟通道受阻，验证工作人员能否按程序撤离和恢复；实验的价值在于发现制度漏洞并修复，不是创造混乱。

## 3. 技术原理与核心内容

典型实验包含稳态假设（如 SLO 的好事件比例与训练 checkpoint 恢复目标）、故障假说、作用范围、影响预算、观测信号、注入动作和回滚/紧急停止。可用 Kubernetes pod kill、tc/网络延迟、服务故障注入、AZ 隔离模拟或对象存储 5xx；不同手段不能直接代表真实跨区域共同故障。对概率性中断需说明注入频率与持续时长；运行后做实验前后对比、恢复时间和用户影响追踪。不能在未获授权的生产环境进行破坏性试验。

## 4. 工程实践与设计权衡

AI Infra 可先从 staging 的单 GPU worker 退出、NCCL 初始化超时、单节点 Device Plugin 故障、模型权重下载失败、KV cache 服务不可用开始；验证 job 重试/幂等、checkpoint 原子性、Kueue requeue、推理多副本 failover。生产实验限定租户、节点池与流量比例，预设 abort threshold（例如错误预算 burn rate、受影响请求数）、on-call 值守和自动回滚。对用户数据/密钥采取保护，记录实验版本与产出问题单。

## 5. 易混概念与边界

混沌工程验证在未知故障下的稳态保持或恢复；压测主要变化负载，故障注入主要变化依赖/资源健康状态。故障演练不是合规审查或完整灾难恢复证明，单次成功不能保证所有共因故障都可控。

## 6. 中等难度面试题（含参考答案）

1. **问：为什么不建议直接从生产集群“随机 kill 全部 GPU Pod”开始？** 答：缺少作用范围、失败预算和自动恢复保证会伤害在线用户与训练数据；应先设定稳态假设、受控故障半径、停止条件，从 staging/单节点逐步扩展。

2. **问：哪些证据能说明一次训练故障注入实验成功？** 答：在节点退出后作业按预设 RTO 从正确 checkpoint 恢复，训练进度/数据未异常重复，重试不产生不可控成本，指标与日志可关联，实验异常已总结。

## 7. 中等难度考试题（含解析）

1. **题：实验限定最多影响 2% 的 500 个推理 Pod，最多能选几个 Pod？** 解：`500×0.02=**10 Pods**`，仍需确认是服务容量占比还是 Pod 数占比。

2. **题：某实验注入依赖故障持续 90s，恢复又花 45s，若服务从注入一开始完全不可用，总不可用时长？** 解：`90+45=**135s**`，假设两个阶段不重叠。
