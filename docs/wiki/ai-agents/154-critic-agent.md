# Critic Agent（批评者智能体）

> AI Agents · 专题：多智能体协作 · 工程角色定义；职责、权限与真实验收依具体系统为准

## 1. 核心定义

**Critic Agent（批评者智能体）**：Critic Agent（批评者智能体）是对方案、输出或行动计划主动寻找错误、漏洞、反例与优化空间的角色，目标是提升最终结果的稳健性。它可嵌入生成—评估—修订循环，但仅提供批评并不能证明修订后已满足验收条件。

**适用边界：**Critic 可以与生成器使用不同模型或数据，但彼此可能共享同样偏见。对不确定的事实不应为了‘尖锐’而编造缺陷，对高后果操作也不能自行授权。

## 2. 形象理解

像设计评审会上负责挑出边界条件、最坏情况和潜在故障的红队成员。

**类比的局限：**提出风险并不等于风险真实存在或已经被修复，批评必须有可验证依据。

## 3. 技术原理与核心内容

将 candidate y、rubric R 和证据 E 交给 critic，生成 `findings=[{claim,location,risk,evidence,proposed_test}]`，由 optimizer 修订 y'，之后执行外部验证。Critic 可针对完整性、性能、隐私与注入风险分维度运行，但要设置 max_rounds、成本预算和 stop_condition，防止漫无目的反复修改。

## 4. 工程实践与设计权衡

**工程案例：**Agent 提出‘删除所有旧日志即可腾出空间’，Critic 指出日志保留政策、事故溯源和权限问题，并要求先查盘占用与保留期。最终仍由审计/授权工具确认后才能删除。

**失败模式与验证：**模型凭空编造漏洞、引用未核对、评估指标反复变化导致循环震荡、因为批评就主动执行危险修复。通过明确反例、客观测试、问题命中率和误报率评估 Critic 的增益。

## 5. 关联知识与易混辨析

Critic Agent 偏重发现失败模式与反例；Reviewer Agent 对照正式验收标准给出审查结论；Evaluator–Optimizer 是有反馈循环的整体模式；Red Teaming 是刻意对抗评估的专业流程。

## 6. 中等难度面试题（含参考答案）

1. **问：Critic 输出 10 个错误是否代表质量一定更高？** 答：不一定；必须区分真实缺陷、误报和重要性，评价定位/证据和修复收益，而不是数量。
2. **问：为什么批评者不能直接调用删除工具修复发现的问题？** 答：批评是建议，执行需用户意图、授权、预检查、审批与真实业务工具校验，尤其是不可逆副作用。

## 7. 中等难度考试题（含解析）

1. **题：Critic 提出 8 个缺陷，其中 5 个经测试确认为真，报告的 precision？** 解：5/8=62.5%；还需调查未发现的实际缺陷才能计算 recall。
2. **题：一轮批评耗 1.5 秒、修订耗 2 秒，最多 3 轮且顺序执行，总模型时间上限？** 解：3×(1.5+2)=10.5 秒，忽略外部验证。
