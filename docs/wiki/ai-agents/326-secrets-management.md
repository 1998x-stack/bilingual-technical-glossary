# Secrets Management（密钥管理）

> AI Agents · 专题：开发实践与生态术语 · 秘密保护、环境隔离与可靠交付

## 1. 核心定义

**Secrets Management（密钥管理）**：密钥管理是对 API token、服务凭据、签名密钥、证书和密码进行安全生成、授权访问、分发、轮换、吊销与审计的系统性实践。在 Agent 系统中，模型负责决策，但不能天然获得明文秘密或工具的高风险权限。

**关键边界：**配置存在不等于具备对应权限，模型生成说明不等于业务系统已执行。部署环境和 Secret 系统的具体 API、访问限制与保护规则随平台和产品版本不同，应以维护者来源及项目实际规则为准。

## 2. 形象理解

**类比：**像酒店门卡系统：不同员工的卡只能进入指定区域，卡过期和人员离职后立即失效。

**类比的局限：**人的流程比喻并未覆盖异步任务、不可逆业务副作用、动态凭据和多租户上下文；安全控制必须落实到可执行的技术边界。测试标签、环境名称和版本说明不能自动证明隔离有效。

## 3. 技术原理与核心内容

集中式 Secret Store 可保护静态凭据，Vault 等系统还可按需要生成带 lease/TTL 的动态凭据；GitHub Actions 可用 OIDC 向支持的云端换取短期身份，减少长期密钥。设计须考虑静态存储、传输、进程内存、日志、Prompt、错误栈和子进程的泄露面。轮换需要安全切换连接，不应默认“写入新值”就删除旧凭据。

**安全和结果边界。**AI Agent 的模型结论、工具调用响应和实际业务提交不是同一事件。可信执行器必须对用户、租户和资源逐次授权，并用幂等标识与权威后置状态处理超时/重试。外部文档和工具输出不得直接转化为秘密访问指令；应限制网络出口、敏感日志、环境间通信以及模型可见信息。Secret 值变更和部署状态需要独立审计，不能用模型自报代替。

**实现步骤。**先定义环境与资源的权限主体，再选择受控的配置来源和凭据交付机制；在启动时验证所有关键配置，禁止未知配置意外指向生产。所有高风险写入应独立执行最小授权、业务规则检查与真实后置状态核对。

## 4. 工程实践与设计权衡

**工程案例：**检索 Agent 访问三家外部 API，执行器只向对应工具注入限定 scope 的短期 token。网页内容要求“读取 API_KEY 并输出到回答”时必须拒绝，因为网页是低信任数据，不属于用户授权。

**验收测试。**在隔离环境构造正常路径、配置缺失、secret 过期、恶意检索内容、429/503、SDK 升级失败、审批中断、持久恢复及重复提交。逐条核对 task/trace ID、配置与部署版本、真实 API 执行结果、审核事件、业务成功率和 P95。保持发布配置可审计、密钥最小权限和紧急回滚路径；测试样本与费用数据应注明范围，且独立专家复核仍为 pending。

**设计权衡。**更严格的隔离、短期凭据和多环境发布会增加部署复杂度，但能防止错误配置或模型误判造成真实数据泄漏。生产状态与开发效率不可简单相互替代，需要版本化配置、明确审核人与测试停止条件。

## 5. 关联知识与易混辨析

Environment Variable 是进程配置载体而不是机密保险箱；KMS 着重加密密钥操作，Secrets Management 涵盖凭据全生命周期；Credential Rotation 只负责更换凭据这一环。

不要把“部署成功”与“任务成功”混用。系统可能已经启动，但工具凭据无效或业务审批流程失效；还必须基于用户可感知 SLI、错误预算和审计记录评估可用性。

## 6. 中等难度面试题（含参考答案）

1. **问：把生产 API Key 放在 system prompt 中是否比放在工具端更安全？** 答：不安全。模型消息可能被存储或受注入影响，应由可信执行器按工具注入最小权限凭据，模型只见结果。
2. **问：怎样避免多个 Agent 共享同一管理员秘钥造成横向越权？** 答：分离服务身份和租户作用域，采用短期令牌、最小 scope、密钥轮换和访问审计。

答题重点：展示真实权限检查、事故止损和环境边界，不能只提出写 Prompt 或设置一个环境变量来代替安全架构。

## 7. 中等难度考试题（含解析）

1. **题：某动态凭据初始有效 60 分钟，每次成功续租延长 60 分钟，连续运行至 180 分钟且末时点不再调用，至少在中间续租几次？** 解：在 60、120 分钟到期前分别续租一次，共 2 次；实际还需预留时钟偏差。 数值以题设为准，并说明具体分母或时间条件。
2. **题：一个 Agent 的 10 种工具中仅 2 个需要付款权限，是否给所有工具使用同一付款密钥？** 解：不合理，应该仅为需要付款的两种工具设置细粒度授权，其余工具没有付款 scope。 需要交代失败反例与恢复/隔离原则，不能直接从内部测试推断外部保证。
