# Lifecycle Hook（回调钩子）

> AI Agents · 专题：工程化、成本与可观测性 · 可靠性与生产治理

## 1. 核心定义

**Lifecycle Hook（回调钩子）**：Agent Runtime 在模型、工具或 Agent 启停等生命周期事件发生时调用的扩展接口，用于日志、指标、资源管理和受控扩展。各 SDK 的触发顺序、作用域和异常语义不同，不可假设全局统一。

**定义和适用边界：**本概念需要指明作用的流程阶段、测量窗口、具体版本或权限边界。运行时 Hook 的实现、服务协议的条款以及断路器的策略不是行业唯一标准。应把观测到的系统事件与业务真实结果区分开，不能通过对模型回答的文字检查来代替后端验收。

## 2. 形象理解

**类比：**像生产线在指定工位设置的质检触发器，工件到站时执行一次检查。

**类比的局限：**类比不涵盖分布式网络、并发状态、数据隐私和业务幂等；现实系统还必须处理工具的未知执行状态。它只提供直观入口，不意味着该机制能保证每一步调用都成功或完全可靠。

## 3. 技术原理与核心内容

典型事件为 on_agent_start/on_agent_end、on_llm_start/on_llm_end 和工具 start/end。OpenAI Agents SDK 区分 RunHooks 与 AgentHooks；记录 task_id、attempt_id、时间和事件来源。重复重试、异常、恢复时 hook 可能不按理想成对触发，必须验证框架适用版本。

**执行与观测边界。**AI Agent 的模型调用、工具选择、工具执行、业务提交与最终结果验收是不同步骤。写入权限必须由可信服务端按用户/资源检查；超时状态并不意味着外部事务未执行。日志或监控可以采样、延迟、失败，不能单凭一条消息判定业务完成。调用重试要结合幂等键与真实后置状态，高风险操作还要有具体参数绑定的审批。

**实施流程：**先定义可信用户目标与资源范围，随后建立 Agent 模型和工具事件的结构化观测。按照能力、业务风险和 SLI 选择是否继续执行、短路、升级人工或降级；失败后通过权威业务状态和相关 Trace 核对结果。不同层的保护机制必须组合使用，不能把一项机制当成所有错误的通用解药。

## 4. 工程实践与设计权衡

**工程示例：**一个工具 hook 在开始时记时间、结束时生成指标，但若工具抛异常，需用异常处理或 finally 记录失败并释放资源；同时防止 hook 输出完整 system prompt。

**故障注入与验收。**在隔离环境模拟 HTTP 429/503、工具超时、局部恢复、队列积压、审批变更和模型回答成功但业务未落库，验证指标、状态机和回调事件是否一致。记录 task_id、trace_id、时间窗、业务成功分母、恢复时延和人为处理动作。明确日志隐私、采样遗漏、阈值抖动和告警成本的权衡；不将演练数据包装成真实生产可靠性指标。

**设计权衡：**保护越强可能增加拒绝率、延迟与审查成本；保护过弱又会在持续错误时扩大费用和副作用。要在 SLO、业务风险和资源预算之间做有条件选择，并为每项阈值设置可回滚配置和独立测试。

## 5. 关联知识与易混辨析

Hook 是可扩展的回调，不是强制授权中间件。Orchestration Graph Node 是可调度步骤；hook 未必有可靠事务语义。

比较相邻术语时还应回答谁触发、何时触发、是否产生持久副作用、谁拥有最终批准权。对外 SLA 必须按实际协议界定；SDK Hook 也不能被默认视为不可绕过的事务边界。

## 6. 中等难度面试题（含参考答案）

1. **问：能否把付款的唯一权限检查放在 on_tool_start 中？** 答：不能，hook 可能被跳过、出错或重复，真实写入必须由 API 服务端执行 ACL 与审批。
2. **问：共享 Agent 的并发 Hook 为何不能直接更换全局工具对象？** 答：共享可变对象会跨运行竞态，产生工具可见性与授权漂移，需按运行隔离配置。

面试评价重点是技术条件与失败路径，尤其要说明如何通过可观察数据验证修复并避免额外的风险和费用。

## 7. 中等难度考试题（含解析）

1. **题：100 次模型调用都触发一次 start 和一次 end，理想回调多少次？** 解：100×2=200 次；实际异常路径需单独统计。 结果依题设单位和假设成立，并非生产实测。
2. **题：调用失败导致 on_tool_end 未触发，如何补救耗时监控？** 解：在异常路径终结 Span/事件，记录失败状态并核对真正执行时间，不得默认成功。 需说明隐含前提和常见错误推导，不能把单个指标当作完整业务结论。
