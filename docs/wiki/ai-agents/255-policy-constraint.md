# Policy Constraint（策略约束）

> AI Agents · 专题：安全防护与治理 · 按最新基准版本与真实执行权限界定结论

## 1. 核心定义

**Policy Constraint（策略约束）**：Policy Constraint（策略约束）是组织、用户或系统为 Agent 设定的必须遵守的业务、安全和合规规则，例如只读访问、付款上限、禁止跨租户读取、需要人工批准及数据保留限制。它定义行为边界，不只是模型的一条建议。

**适用边界：**策略必须有明确优先级、适用主体、资源和执行点；用户低信任输入或工具文档中的声明不能自动覆盖高层安全规则。模型可以协助解释政策，但正式允许/拒绝决定应由受控政策引擎和真实资源权限作出。

## 2. 形象理解

像企业出差政策规定每笔报销金额上限和审批层级，不因员工聊天中写‘经理已经同意’便失效。

**类比的局限：**政策文字可能模糊或更新，执行程序需有版本、例外审批和冲突解释流程，而不是任意猜测。

## 3. 技术原理与核心内容

将政策描述为 `Policy={subject,action,resource,context,conditions,version,priority}`，在执行敏感 Tool 前调用 policy engine，传入可信身份、目标对象及金额/时间约束。OPA/Rego 等 policy-as-code 使 allow/deny 可测试，默认拒绝未知或缺字段输入；同时将审批结果与 arguments_hash、resource_revision 绑定。写入 audit decision，旧策略决议不得被跨 tenant 缓存。新增策略时运行正例/负例回归，核验 override 需要显式授权。

## 4. 工程实践与设计权衡

**工程案例：**企业 Agent 只能读取本租户预算并在未获人工签核时不得提交任何超过 1000 元的采购。即使模型回复‘批准完成’，策略引擎也必须依据真实授权人、订单 ID 和当前金额决定拒绝或允许。

**失败模式与验证：**在 prompt 中写策略却无执行 gate、信任用户自报角色、策略默认 allow、不同微服务的 policy_version 漂移。以跨租户、金额边界、过期审批、策略变更和无身份输入测验。

## 5. 关联知识与易混辨析

Policy Constraint 是规则本身；Guardrail 是检查规则的机制；Authorization 是对特定主体/操作做许可判定；Safety Confirmation 是用户对某具体高影响动作的明确确认。

## 6. 中等难度面试题（含参考答案）

1. **问：为什么 Policy Constraint 需要在后端落实而不只写进模型提示？** 答：提示可能被忽略或注入覆盖，后端能够独立依据可信上下文拒绝越权操作。
2. **问：策略缺少角色字段时应该默认允许还是拒绝？** 答：敏感业务应 fail-closed 拒绝，并给出安全可修复的缺字段原因。

## 7. 中等难度考试题（含解析）

1. **题：策略允许每笔付款金额至多 1000 元，申请 1001 元且无额外审批应怎样处理？** 解：拒绝或进入合法审批流程。
2. **题：三个策略条件采用 AND：主体授权、资源归属、金额合规，只有前两项为真时是否可执行？** 解：不能，AND 条件需全部为真。
