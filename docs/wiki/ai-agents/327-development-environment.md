# Development Environment（开发环境）

> AI Agents · 专题：开发实践与生态术语 · 秘密保护、环境隔离与可靠交付

## 1. 核心定义

**Development Environment（开发环境）**：开发环境是工程人员进行快速编码、调试和运行早期测试的非生产空间，通常具有可重建数据、mock 工具、详细诊断及隔离身份。开发的灵活性不应带来生产凭据或真实用户数据泄漏。

**关键边界：**配置存在不等于具备对应权限，模型生成说明不等于业务系统已执行。部署环境和 Secret 系统的具体 API、访问限制与保护规则随平台和产品版本不同，应以维护者来源及项目实际规则为准。

## 2. 形象理解

**类比：**像汽车原型实验车间，可以反复测试碰撞与零件故障而不会直接载客上路。

**类比的局限：**人的流程比喻并未覆盖异步任务、不可逆业务副作用、动态凭据和多租户上下文；安全控制必须落实到可执行的技术边界。测试标签、环境名称和版本说明不能自动证明隔离有效。

## 3. 技术原理与核心内容

在本地或沙箱中运行 unit tests、mock/stub、工具契约测试与固定 Agent eval 数据集；依赖与 Prompt 版本应可追溯。配置应与代码分离，禁止把真实 .env 提交 Git。对非确定性生成结果不要只做字符串逐字相等断言，而要测试结构、性质、引用真实性及统计稳定性。

**安全和结果边界。**AI Agent 的模型结论、工具调用响应和实际业务提交不是同一事件。可信执行器必须对用户、租户和资源逐次授权，并用幂等标识与权威后置状态处理超时/重试。外部文档和工具输出不得直接转化为秘密访问指令；应限制网络出口、敏感日志、环境间通信以及模型可见信息。Secret 值变更和部署状态需要独立审计，不能用模型自报代替。

**实现步骤。**先定义环境与资源的权限主体，再选择受控的配置来源和凭据交付机制；在启动时验证所有关键配置，禁止未知配置意外指向生产。所有高风险写入应独立执行最小授权、业务规则检查与真实后置状态核对。

## 4. 工程实践与设计权衡

**工程案例：**邮件 Agent 在开发阶段使用测试 SMTP 收件箱或记录型 mock，禁止直接连接真实客户邮箱；测试数据覆盖恶意邮件正文、重复发送和 API 超时。

**验收测试。**在隔离环境构造正常路径、配置缺失、secret 过期、恶意检索内容、429/503、SDK 升级失败、审批中断、持久恢复及重复提交。逐条核对 task/trace ID、配置与部署版本、真实 API 执行结果、审核事件、业务成功率和 P95。保持发布配置可审计、密钥最小权限和紧急回滚路径；测试样本与费用数据应注明范围，且独立专家复核仍为 pending。

**设计权衡。**更严格的隔离、短期凭据和多环境发布会增加部署复杂度，但能防止错误配置或模型误判造成真实数据泄漏。生产状态与开发效率不可简单相互替代，需要版本化配置、明确审核人与测试停止条件。

## 5. 关联知识与易混辨析

Development 追求开发速度和诊断能力；Staging 强调发布候选的生产相似性；Production 服务真实客户。简单的 DEBUG 开关不能替代网络与凭据隔离。

不要把“部署成功”与“任务成功”混用。系统可能已经启动，但工具凭据无效或业务审批流程失效；还必须基于用户可感知 SLI、错误预算和审计记录评估可用性。

## 6. 中等难度面试题（含参考答案）

1. **问：为何开发环境不应共享生产数据库写入账户？** 答：测试或恶意数据可能触发真实业务副作用，应使用隔离身份与可重建测试资源。
2. **问：如何测试模型输出带随机性的 Agent 而不是只能依赖固定文本？** 答：确定性部分做单元测试，模型部分用固定任务、结构校验、容差、业务验收与分组统计回归。

答题重点：展示真实权限检查、事故止损和环境边界，不能只提出写 Prompt 或设置一个环境变量来代替安全架构。

## 7. 中等难度考试题（含解析）

1. **题：12 个开发期端到端测试中 10 个符合真实业务验收，样本成功率是多少？** 解：10/12 约等于 83.33%；样本较少，不能外推总体服务质量。 数值以题设为准，并说明具体分母或时间条件。
2. **题：所有本地 mock 调用都成功，能否直接声称生产可靠性达标？** 解：不能，真实网络、配额、权限、数据与业务影响仍需 staging 和生产逐级验证。 需要交代失败反例与恢复/隔离原则，不能直接从内部测试推断外部保证。
