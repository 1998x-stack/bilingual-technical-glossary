# Throughput（吞吐量）

> AI Agents · 专题：工程化、成本与可观测性 · 执行容量、任务调度与资源治理

## 1. 核心定义

**Throughput（吞吐量）**：系统单位时间内处理的有效任务、请求或 token 数，常写为 tasks/s、requests/s、tokens/s。必须明确是入口接收量、完成量还是成功完成量；Agent 多步骤链路中的最慢瓶颈常决定稳态吞吐。

**适用边界：**Agent 的任务可能包含模型推理、远程工具、等待人工和不可逆业务写入，因此性能指标需写明测量对象、成功判定、时间周期及硬件/服务配额。算法的理想公式不自动等于实测性能；其他系统的吞吐与延迟数据不能不加条件地移植到 Agent 环境。

## 2. 形象理解

**类比：**像食堂每小时真正完成多少份套餐，而不是有多少人走进门。

**类比的局限：**原材料准备可能并行，最后出餐可能串行；排队人数也不等于成功出餐量。 真实工作流的重试、排队、限流与成本上限使“更多资源=更快”经常不成立，需建立可验证的性能假设。

## 3. 技术原理与核心内容

用 X=N_completed/Δt 计算稳态输出率。对于稳定系统可用 Little 定律 L=λW 关联在途任务数 L、到达率 λ 和平均逗留时间 W；前提是统计口径和稳定性匹配。多工具 Agent 的 fan-out、限流、缓存命中与重试会改变有效吞吐。

**执行链与负载模型。**用户任务进入运行时，经队列/调度器、模型和工具调用、状态提交、验收。每一级都有容量、等待时间和失败状态。测量时区分到达、尝试、完成与成功完成的计数；应明确跨服务重试是否被重复统计。对于外部写入，必须依据真实后置状态与幂等键判定，不能只信任模型自然语言。

**测量与调优步骤。**先确定容量瓶颈，再选择控制入口流量、排队深度、fan-out 数或执行单元；对共享资源使用原子计数或一致性契约，防止各子 Agent 独立判断额度造成系统性超支。面向用户的 SLO 和真实后置状态应优先于模型自报成功。

## 4. 工程实践与设计权衡

**工程案例：**10 个并发 Agent 同时处理查询，模型较快却被每秒最多 5 次的搜索 API 限流；即使增加模型副本，依赖搜索的任务吞吐仍有上限，需要缓存/批处理或减轻该瓶颈。

**工程边界与验证。**通过受控压测改变任务到达率、并发/并行度、工具超时与下游限额，采集队列深度、吞吐、P95/P99、429/503 和实际业务完成率。观察瓶颈由 CPU、I/O、远程模型、数据库或工具配额中哪一部分决定。加载测试需避免真实费用或客户副作用，并把所有数值示例标为教学假设；必须设置真实成本预算与停机条件。

**权衡。**增加并行度会引入同步和共享瓶颈；过于激进的限流可能压低吞吐，而过于宽松则可能引起尾延迟爆炸。应综合错误预算、成本、用户体验和公平性选择策略。未知状态写入不能因为重试而重复触发付款或发信。

## 5. 关联知识与易混辨析

Throughput 是完成速率，Latency 是单任务耗时，Concurrency 是重叠在途量；三者相关但不能用一个指标替代另一个。

评审设计时先列清楚测量单位：tasks/s、requests/s、tokens/s、在途数、任务时延、费用与配额是不同的量。还要区分逻辑任务与单次 attempt，避免将重试造成的请求量增长解释成真正业务产能增长。

## 6. 中等难度面试题（含参考答案）

1. **问：为什么提升并发数有时不会增加任务吞吐？** 答：存在下游限流、CPU 饱和或锁竞争时，只会增加排队与 P99 延迟；需按瓶颈扩容和背压。
2. **问：如何区分入口 QPS 与有效业务吞吐？** 答：入口只计接收请求，业务吞吐必须以真实完成/提交为准，区分失败和重试。

答题应说明假设、适用场景和实际验证指标；既能解释算法机制，也要指出哪些高风险工具不能仅因“性能最优”而绕过授权。

## 7. 中等难度考试题（含解析）

1. **题：300 个已完成任务耗时 2 分钟，平均吞吐量是多少？** 解：300/120=2.5 tasks/s。 **检验：**明确单位和数学条件，计算结果只对题设成立。
2. **题：稳定系统到达率 4 tasks/s、平均在系统内停留 3s，平均在途数？** 解：用 L=λW=4×3=12 个任务；假设稳态、单位一致。 **检验：**需要描述边界、瓶颈或反例，不能把单一指标误当作完整系统质量。
