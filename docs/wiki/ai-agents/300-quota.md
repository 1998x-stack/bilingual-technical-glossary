# Quota（请求配额）

> AI Agents · 专题：工程化、成本与可观测性 · 执行容量、任务调度与资源治理

## 1. 核心定义

**Quota（请求配额）**：一定结算或计量周期内允许某主体消耗的请求、token、费用或其他资源总额度，常用于租户公平、计费与预算治理。Quota 的统计单位和重置时点必须明确。

**适用边界：**Agent 的任务可能包含模型推理、远程工具、等待人工和不可逆业务写入，因此性能指标需写明测量对象、成功判定、时间周期及硬件/服务配额。算法的理想公式不自动等于实测性能；其他系统的吞吐与延迟数据不能不加条件地移植到 Agent 环境。

## 2. 形象理解

**类比：**像每月图书馆借阅上限：本月借完不能因为这一分钟很闲就继续借。

**类比的局限：**额度未耗尽也不代表当前系统有处理能力；瞬时高峰仍需要速率和并发保护。 真实工作流的重试、排队、限流与成本上限使“更多资源=更快”经常不成立，需建立可验证的性能假设。

## 3. 技术原理与核心内容

Quota 通常按用户/租户/模型/工具/周期计数；记录 spent、reserved、remaining，避免并行请求在检查后同时超额（TOCTOU）。周期重置要考虑时区、结算对账和失败请求是否扣量。异步任务宜先预留预算、完成后结算或退款。

**执行链与负载模型。**用户任务进入运行时，经队列/调度器、模型和工具调用、状态提交、验收。每一级都有容量、等待时间和失败状态。测量时区分到达、尝试、完成与成功完成的计数；应明确跨服务重试是否被重复统计。对于外部写入，必须依据真实后置状态与幂等键判定，不能只信任模型自然语言。

**测量与调优步骤。**先确定容量瓶颈，再选择控制入口流量、排队深度、fan-out 数或执行单元；对共享资源使用原子计数或一致性契约，防止各子 Agent 独立判断额度造成系统性超支。面向用户的 SLO 和真实后置状态应优先于模型自报成功。

## 4. 工程实践与设计权衡

**工程案例：**企业 Agent 每天最多使用 100,000 输出 token；多个子 Agent 并发可能共同预留超过余额。可信执行器需原子扣减并阻止跨租户借用。

**工程边界与验证。**通过受控压测改变任务到达率、并发/并行度、工具超时与下游限额，采集队列深度、吞吐、P95/P99、429/503 和实际业务完成率。观察瓶颈由 CPU、I/O、远程模型、数据库或工具配额中哪一部分决定。加载测试需避免真实费用或客户副作用，并把所有数值示例标为教学假设；必须设置真实成本预算与停机条件。

**权衡。**增加并行度会引入同步和共享瓶颈；过于激进的限流可能压低吞吐，而过于宽松则可能引起尾延迟爆炸。应综合错误预算、成本、用户体验和公平性选择策略。未知状态写入不能因为重试而重复触发付款或发信。

## 5. 关联知识与易混辨析

Quota 管长期总量，Rate Limiting 管短期速度，Cost Budget 关注费用上限而不局限资源单位。Quota 可以按 token 或请求计，不等于固定现金价格。

评审设计时先列清楚测量单位：tasks/s、requests/s、tokens/s、在途数、任务时延、费用与配额是不同的量。还要区分逻辑任务与单次 attempt，避免将重试造成的请求量增长解释成真正业务产能增长。

## 6. 中等难度面试题（含参考答案）

1. **问：如何为 10 个并行子 Agent 保证共享配额不超支？** 答：采用原子预留/扣减的共享账本，完成后按计费结果结算，分支不可本地猜测余额。
2. **问：如何处理调用超时但可能已经计费的使用量？** 答：对账权威 usage/账单记录，区分未执行、未知和已完成，避免盲目退款或重复计量。

答题应说明假设、适用场景和实际验证指标；既能解释算法机制，也要指出哪些高风险工具不能仅因“性能最优”而绕过授权。

## 7. 中等难度考试题（含解析）

1. **题：题设日配额 10,000 tokens，已用 6,200、预留 1,500，还可新预留多少？** 解：10,000−6,200−1,500=2,300 tokens。 **检验：**明确单位和数学条件，计算结果只对题设成立。
2. **题：每租户限制 1,000 calls/day，但一次请求可耗时很长，为什么仍有风险？** 解：配额不限制并发和任务时长，仍需在途连接上限、deadline 与资源预算。 **检验：**需要描述边界、瓶颈或反例，不能把单一指标误当作完整系统质量。
