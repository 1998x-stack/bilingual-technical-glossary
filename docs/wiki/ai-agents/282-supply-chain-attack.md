# Supply Chain Attack（供应链攻击）

> AI Agents · 专题：智能体攻击与风险 · 威胁建模、可信执行与工程治理

## 1. 核心定义

**Supply Chain Attack（供应链攻击）**：攻击者通过第三方依赖、模型、容器镜像、Skill 脚本、插件发布源或构建流程操纵 Agent 的最终行为。风险横跨开发、构建、部署和运行多个组织的信任链。

**关键边界：**不能将可能导致风险的模型文本、已经发起的工具调用与真正完成的业务动作混为一谈。若无危险权限、若后端独立拒绝，或若动作未被提交，则需要精确描述实际风险状态。厂商工具能力及具体协议版本可能改变，研究时应核对原始文档，勿假设每种 Agent 使用同一工具实现。

## 2. 形象理解

**类比：**餐厅厨师认真执行菜谱，却收到被调包的食材，问题发生在采购供应链。

**类比的局限：**现实系统具有多个访问主体、工具适配器和异步状态；单一比喻只表达部分因果关系，不能证明某种输入必然触发越权或账单损失。应该回到实际数据流，找出哪里从低信任信息转变为高风险操作。

## 3. 技术原理与核心内容

建立依赖清单与 SBOM、锁版本、验证来源和签名/哈希、扫描许可证与构建产物；动态 Skill 需审查脚本、外联、文件权限和更新机制。可复现构建和供应方证明仍需与运行时隔离相结合。

**风险模型。**Agent 系统中可信用户目标、模型推断、外部工具说明与执行后的真实状态属于不同信任层。普通自然语言、结构化字段和网页内容即使被模型采纳，也不能获得执行授权。需要将 tool discovery、参数校验、资源 ACL、操作审批和后置状态核对分开；对不可逆写入要求幂等性和错误恢复。不能把模型回复“我拒绝”当作没有副作用的证据，也不能把 API 超时直接认定为未提交。

**系统设计的核对链：**明确用户需要什么→列出模型可建议的动作→为工具定义最小资源权限→验证请求与参数→确认外部服务的后置状态。对于外部第三方的代码、工具或配置，必须额外记录版本、来源与变更；对于自动化循环，还应明确调用和费用上限。

## 4. 工程实践与设计权衡

**工程场景：**团队从不明位置复制 Agent Skill，其中脚本尝试读取本机秘密并发往外部。应审查包内容与维护者，隔离运行并禁止不必要凭据挂载。

**可复核的工程验证。**构建隔离测试账户、合成 canary 和受控工具，明确模拟的攻击入口、业务动作与预期权限。记录每次任务的模型建议、真实调用、后端判定、用户审批、费用和权威业务后置状态。分别计算攻击触发率、拦截率、误报率与真实损害，而不是只报一个笼统“安全率”。覆盖工具版本变化、动态加载、租户切换、重试、超时、并行分支及敏感信息出现在日志/监控的情况，确保假设条件可重复。

**常见失败模式和取舍：**通配账号、任意外联、提示词中保存 secret、缺少限额和模糊的工具描述，都可能显著放大错误。收紧权限、审核依赖或强化审批会提高工程复杂度和延迟，但可限制不可逆影响。应结合任务风险和实际业务后置状态，制定分级安全策略和回滚流程。

## 5. 关联知识与易混辨析

Tool Poisoning 可能从插件供应链发生，但 Supply Chain Attack 还涉及模型权重、依赖库、训练数据和交付管道。

应区别攻击入口、被污染对象、造成的错误行动与经济/数据后果。前置知识包括 Agent Loop、Tool Calling、Trust Boundary、Idempotency、Human Approval、Observability；它们的职责不同，不能用一个安全标签覆盖整条执行链。

## 6. 中等难度面试题（含参考答案）

1. **问：为什么锁文件不等于完全安全？** 答：固定一个恶意版本仍可能受攻击；哈希只保证内容一致，还要核对来源、行为和维护安全。
2. **问：下载第三方 Agent 技能后应先验哪些内容？** 答：核对维护者、版本、哈希、所有脚本、依赖、网络目的地、所需权限与可撤回更新。

**面试考查重点：**应解释为什么做出该架构选择、其在失败和恶意输入下是否仍然成立，以及如何用真实工具和业务状态验证；平均回答准确率不能替代风险控制的验证。

## 7. 中等难度考试题（含解析）

1. **题：80 个依赖中 2 个未锁定版本，缺口率？** 解：2/80=2.5%；这不是实际供应链事故发生概率。 题设数字是教学假设。计算应注明数量单位、统计分母与边界，不能作为实测 benchmark 引述。
2. **题：文件哈希匹配但维护者的发布密钥可能泄露，应该怎样决定？** 解：不能仅凭哈希接受，需验证身份签发链、代码内容、行为以及运行时最小权限。 评分时看是否识别真正授权主体、风险发生阶段和真实系统后置条件，而不是只回答一个名称。
