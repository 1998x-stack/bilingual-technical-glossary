# Continuous Delivery (CD)（持续交付）

> AI Agents · 专题：开发实践与生态术语 · 生产治理、可复现变更与持续交付

## 1. 核心定义

**Continuous Delivery (CD)（持续交付）**：持续交付是通过自动化构建、验证、打包和发布准备，使软件持续保持可安全发布状态的工程实践，通常允许在通过质量门槛后由授权人员决定何时真正发布。它不同于每个变更自动上线的 Continuous Deployment，尽管 CD 缩写在产品文档中有时会用于广义部署自动化。

**适用条件：**这里对生产、版本控制和 CI/CD 采用可迁移的工程定义。各组织的审批、发布与支持策略可能不同，特定 GitHub Actions 功能的可用性也取决于计划、仓库配置及权限。不能把 PR 自动测试通过误称已合并 main 或完成领域专家审核。

## 2. 形象理解

**类比：**像食品厂把每批产品自动检测、封装并入待发货仓库，能否立即发货还受运营和质检授权决定。

**类比的局限：**类比未涵盖真实分布式负载、模型随机性、外部副作用和可重复部署限制。即使打包或测试环节全部通过，也不能推出用户业务结果正确；仍需产品级验收与必要的人工授权。

## 3. 技术原理与核心内容

典型流水线由 CI 成功开始：生成带版本/digest 的不可变 artifact→验证依赖与 SBOM→发布候选部署 staging→运行迁移、E2E、安全与 Agent eval→环境批准和生产推广→灰度/监控/回滚。GitHub Environments 可配置 reviewer、环境 secret 和分支保护等（功能依计划和仓库设置）。发布前需绑定模型/Prompt/工具 schema 版本，确保“测试的就是发布的”；对真实外部副作用不能只靠回滚镜像恢复。

**权威边界。**AI Agent 模型回答、工具返回与最终业务后置状态彼此不同。代码审查、测试和配置也不能替代独立的权限校验及真实业务验收。对模型/提示词等非确定性组件，需要以可重复的任务集与条件化质量目标评估；所有外部写入需由可信服务端检查用户、租户与资源授权，并处理未知执行状态和幂等重试。日志不得输出明文秘密。

**关键机制。**先定义变化的提交、配置和构建标识，再记录每一阶段测试的输入、结果及发布门槛；将安全策略、环境权限、成本预算与失败恢复作为流水线的明确条件，而不是依赖提示词承诺。外部业务提交应有独立后置状态与幂等凭据。

## 4. 工程实践与设计权衡

**工程案例：**将 332 篇 Wiki 从候审 PR 合并到 main 时，先保证数据索引校验、Chromium E2E、完整专家审稿与 release artifact 一致，再由授权维护者合并并通过 GitHub Pages 发布。CD 自动化可以构建/部署，但不能替代尚未完成的技术专业审稿。

**工程验证。**在沙箱中演练 schema 迁移、模型响应偏移、工具 429/503、并行工作流、回滚和恢复后的重复写入。记录 commit SHA、artifact digest、Prompt/Model 版本、tool schema 版本、测试结果与 trace ID；检查任务成功率、尾延迟、费用、告警与审计。真实生产灰度应有可执行停止条件和 Runbook。自动化合格不等于独立专家人工技术审核完成。

**设计取舍。**频繁变更可以降低一次发布的差异量，却要求稳定测试和可追溯流水线；过度依赖人工会延迟反馈，完全忽略人工专业复核又可能放行结构上正确而内容错误的文章。应将可自动验证的内容尽量自动化，把领域事实、授权与高风险动作留在明确审核关口。

## 5. 关联知识与易混辨析

Continuous Integration 负责持续验证合并；Continuous Delivery 让软件随时可交付（生产上线可有人工审批）；Continuous Deployment 通常自动把通过流程的变化上线。交付、部署与发布给用户的流量切换也可能是不同事件。

评审时需要严格区分“Git commit 存在”“CI 通过”“产物可部署”“已经正式上线”和“真实用户任务完成”五个状态。每一项分别需要自己的证据来源，不能由后一项自动推导另一项。

## 6. 中等难度面试题（含参考答案）

1. **问：为什么持续交付不要求每次提交都自动部署到生产？** 答：持续交付的目标是产物可安全发布，生产决定可保留人工审批；全自动上线属于更强的持续部署。
2. **问：怎样设计含模型变更的 Agent CD 流程以避免只验证代码、不验证行为？** 答：固定模型/Prompt/Schema 版本、运行 Agent eval/权限与副作用测试、staging 验证、生产灰度与 SLO 回滚。

面试答案应兼顾理论与运行时约束，解释哪些部分可以完全自动化，哪些部分需要独立审核或可追溯的权限批准。

## 7. 中等难度考试题（含解析）

1. **题：每个交付流水线依次经过构建 4 分钟、测试 8 分钟、staging 6 分钟，不含人工审批，最短时间？** 解：4+8+6=18 分钟；假设串行无队列、无其他步骤。 计算结果只在题设条件下成立。
2. **题：CI 全绿、staging 也通过，但专家内容审稿状态 pending，是否可宣称所有 Wiki 已正式审核发布？** 解：不可以。技术审稿是独立质量门槛，应保留 pending 并在发布策略中设置人工批准。 应区分统计样本、项目实际状态和对外发布保证。
