# Runbook（运行手册）

> AI Agents · 专题：工程化、成本与可观测性 · 可靠运维、能力封装与开发集成

## 1. 核心定义

**Runbook（运行手册）**：运行手册是一组针对已知运维情境的可执行步骤与判定条件，用于让值班人员在服务异常时快速定位、止损、恢复和复核。Agent 系统的 Runbook 应覆盖模型、工具、账单、权限和外部业务状态。

**定义边界：**这里的通用工程名称和个别厂商实现要区别对待。工具版本、规范字段、执行权限及可观测语义可能持续变化；不能从“描述存在”推断运行时已安装、用户已授权或动作已经成功。

## 2. 形象理解

**类比：**如飞机紧急检查单，驾驶员按可核实步骤确认关键系统，而不是依赖临场记忆。

**类比的局限：**真实 Agent 包含模型、工具、跨进程调度、业务权限和状态持久化，类比只能说明局部职能。外部文档可以提供资料却不能变成比用户目标更高优先级的行动指令，也不能直接推导脚本执行权限。

## 3. 技术原理与核心内容

推荐结构：触发症状→严重度与影响范围→只读诊断→缓解动作→回滚条件→验证与升级路径→事后复盘。每一步标明负责人、前置权限、可逆性、适用版本与权威监控链接。涉及付款/删除等不可逆动作先检查 idempotency key 和后置状态。

**安全与执行边界。**技能包、SDK 与 ADK 都只能组织能力，不会自动赋予合法用户授权。外部文件或技能元数据可能含恶意说明，须在宿主执行器内落实签名/来源核验、最小权限、租户隔离、参数校验和真实业务后置状态。对不可逆操作使用幂等键，未知提交状态必须向权威系统查询。技能与开发依赖需要明确版本、来源和回滚策略。

**实施顺序：**先依据真实需求定义能力范围和成功判据，再选择工具包或技能的规范与版本，随后验证类型/schema、状态恢复与错误接口，最后以真实业务后置条件验收。工具调用本身不是最终成功条件。

## 4. 工程实践与设计权衡

**工程实例：**Agent 的支付工具连续超时：先查日志与 trace、确认订单是否已付款，必要时暂停新写入并切换只读状态；只有确认未执行后才能决定是否重试。恢复后对账受影响任务，记录时间线。

**工程验证。**使用受控任务集分别测试正常执行、缺失依赖、技能冲突、恶意元数据、过期接口、异常恢复、审批与跨租户访问。日志包含具体 task/trace ID 但不输出凭据。验收不仅检查模型报告的结论，还检查真实工具 API、权限策略与数据库状态。对运行手册进行模拟演练，保证失败路径能止损且能回退；引用依赖具体版本时应复核当前维护者资料。

**权衡：**标准化封装降低重复开发和维护成本，但也可能隐藏自动重试、动态脚本或不透明权限。应为升级设置契约测试、回归验证及回滚方式，明确审核人员和操作日志的保留范围；在技能加载时避免不必要的上下文开销。

## 5. 关联知识与易混辨析

Runbook 是执行操作与核验流程；Alerting 是触发响应，Playbook 有时指更高层场景计划，各组织叫法不完全一致。SOP/自动化脚本也不能替代人工判断所有异常。

需要按“资产/描述”“发现/选择”“实际执行”“业务验证”四个阶段辨析，尤其不能把技能说明、工具 manifest 与已获授权的外部操作混作同一对象。对于供应链或提示词投毒，要把证据来源纳入测试。

## 6. 中等难度面试题（含参考答案）

1. **问：怎样写一份不会在故障时造成重复扣款的 Runbook？** 答：将查询权威交易状态、幂等键、停止条件、权限审核和回滚/升级纳入前置步骤。
2. **问：Runbook 为什么不能只是一组 shell 命令？** 答：需要作用范围、目标、前置条件、风险、回滚、验证及负责人，否则自动执行可能扩大事故。

面试中须解释可迁移原理和产品实现区别，并说明如何验证错误路径和危险权限，不能只答“使用某框架即可”。

## 7. 中等难度考试题（含解析）

1. **题：一次故障 20 分钟检测、15 分钟定位、25 分钟恢复，若连续阶段不重叠，总响应时长？** 解：20+15+25=60 分钟；仅适用于题设连续阶段。 题设数字只是教学假设，写明计算口径和单位。
2. **题：工具服务恢复 HTTP 200，但库存未修复，是否可关闭事故？** 解：不应。还需核实库存/订单等权威业务后置条件及用户可感知 SLI。 完整论证需要指出为什么另一个做法不满足授权、可靠性或版本约束。
