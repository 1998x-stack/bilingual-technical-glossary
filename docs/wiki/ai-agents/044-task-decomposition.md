# Task Decomposition（任务分解）

> 适用领域：AI Agents · 专题：任务规划与决策 · 相关理论与具体产品能力应依据所引来源和版本区分

## 1. 核心定义

**Task Decomposition（任务分解）**：Task Decomposition（任务分解）把复杂目标细化为具有明确输入、输出、前置条件与验收标准的子任务，以降低单次决策难度并允许独立执行、重试或委派。它不仅是把句子拆成步骤，还必须保留业务依赖和权限。

**适用边界：**拆分可以在执行前完成或失败后按需进行；拆得更细不保证更快，协调和上下文传递会增加成本。

## 2. 形象理解

像策划大型展览：分为场地、设备、宣传、安保，每一组有交付物，最终再组织总验收。

**类比的局限：**团队分工过细可能让交接比实际工作更费时，也可能让关键责任无人承担。

## 3. 技术原理与核心内容

从目标 G 生成任务图 `DAG=(V,E)`：每节点含 owner、input、output、acceptance，边 `u→v` 表示 v 依赖 u。可静态分解（先生成全部节点），也可按需分解（执行失败再展开难节点）。结合拓扑序释放任务，最终要核对总体成功谓词而非只统计子任务“已完成”。

## 4. 工程实践与设计权衡

**工程案例：**代码 Agent 为升级依赖分出版本检查、修改代码、测试、发布说明；测试依赖代码修改完成。各节点由最小权限执行器运行，汇总前对变更进行集成测试。

**失败模式与验证：**错误的切分会造成交叉写冲突、证据丢失或子任务各自局部成功但整体失败。要度量失败隔离效果和交接消耗，并为每个写操作定义幂等键。

## 5. 关联知识与易混辨析

Task Decomposition 着重形成子任务集合及其关系；Hierarchical Planning 定义多层抽象与精化方法；Task Dependency 描述节点之间必须满足的先后/资源约束。

## 6. 中等难度面试题（含参考答案）

1. **问：何时不应把任务拆成多个 Agent？** 答：共享状态强耦合、任务很短或每次交接有高额 token/网络开销时，单 Agent 顺序调用工具可能更可靠；用端到端实验而非角色数量判断。
2. **问：如何避免拆分后每个子任务成功但整体目标失败？** 答：把最终验收谓词、接口契约和数据一致性放在汇聚节点校验，并显式跟踪跨任务依赖与异常状态。

## 7. 中等难度考试题（含解析）

1. **题：任务 A=3 min，B=4 min，C=2 min；A 与 B 独立且 C 依赖二者。无限并行时最短完成时长？** 解：max(3,4)+2=6 min；全部串行为 9 min，假定无通信和资源争用。
2. **题：需求“生成报告并发送”拆成写报告、审核、发邮件，为什么邮件不能只依赖写报告？** 解：审核是必需前置条件，图应为写报告→审核→发邮件；若忽略该依赖，可能发送未验收内容。
