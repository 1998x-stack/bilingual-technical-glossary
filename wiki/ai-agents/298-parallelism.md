# Parallelism（并行）

> AI Agents · 专题：工程化、成本与可观测性 · 执行容量、任务调度与资源治理

## 1. 核心定义

**Parallelism（并行）**：多个计算或执行操作在同一时刻实际同时运行，例如不同 CPU 核或加速器设备执行独立工作。并行可作为实现并发的一种方式，但并发不要求同时占用多个计算单元。

**适用边界：**Agent 的任务可能包含模型推理、远程工具、等待人工和不可逆业务写入，因此性能指标需写明测量对象、成功判定、时间周期及硬件/服务配额。算法的理想公式不自动等于实测性能；其他系统的吞吐与延迟数据不能不加条件地移植到 Agent 环境。

## 2. 形象理解

**类比：**厨房里三个厨师同时切菜、烹调和装盘。

**类比的局限：**如果所有人争用唯一烤箱，厨师越多也不保证更快；还有资源竞争与同步成本。 真实工作流的重试、排队、限流与成本上限使“更多资源=更快”经常不成立，需建立可验证的性能假设。

## 3. 技术原理与核心内容

计算密集任务可用多进程或设备并行，任务拆分后通过分区、聚合和同步合并结果。理论加速受串行部分与通信开销约束：Amdahl 定律 S(P)=1/((1-f)+f/P)，其中 f 是可并行比例，P 为处理单元数。

**执行链与负载模型。**用户任务进入运行时，经队列/调度器、模型和工具调用、状态提交、验收。每一级都有容量、等待时间和失败状态。测量时区分到达、尝试、完成与成功完成的计数；应明确跨服务重试是否被重复统计。对于外部写入，必须依据真实后置状态与幂等键判定，不能只信任模型自然语言。

**测量与调优步骤。**先确定容量瓶颈，再选择控制入口流量、排队深度、fan-out 数或执行单元；对共享资源使用原子计数或一致性契约，防止各子 Agent 独立判断额度造成系统性超支。面向用户的 SLO 和真实后置状态应优先于模型自报成功。

## 4. 工程实践与设计权衡

**工程案例：**Agent 同时调用 3 个互不依赖的检索源，在网络层重叠等待属于并发；若 3 个嵌入批次由独立 GPU 同时计算则体现真正的计算并行。错误合并可能破坏结果次序与去重。

**工程边界与验证。**通过受控压测改变任务到达率、并发/并行度、工具超时与下游限额，采集队列深度、吞吐、P95/P99、429/503 和实际业务完成率。观察瓶颈由 CPU、I/O、远程模型、数据库或工具配额中哪一部分决定。加载测试需避免真实费用或客户副作用，并把所有数值示例标为教学假设；必须设置真实成本预算与停机条件。

**权衡。**增加并行度会引入同步和共享瓶颈；过于激进的限流可能压低吞吐，而过于宽松则可能引起尾延迟爆炸。应综合错误预算、成本、用户体验和公平性选择策略。未知状态写入不能因为重试而重复触发付款或发信。

## 5. 关联知识与易混辨析

Parallelism 关注物理同时执行；Concurrency 是任务生命周期重叠。Fan-out 是结构模式，不保证底层一定有足够硬件实现并行。

评审设计时先列清楚测量单位：tasks/s、requests/s、tokens/s、在途数、任务时延、费用与配额是不同的量。还要区分逻辑任务与单次 attempt，避免将重试造成的请求量增长解释成真正业务产能增长。

## 6. 中等难度面试题（含参考答案）

1. **问：为什么线程数量等于 8 不代表得到 8 倍加速？** 答：串行比例、内存带宽、锁与调度成本都限制加速；还需看运行时是否真正并行。
2. **问：对含串行审批步骤的 Agent 工作流，如何评估并行收益？** 答：画出依赖 DAG，找关键路径与串行步骤，再评估独立分支并行和汇合代价。

答题应说明假设、适用场景和实际验证指标；既能解释算法机制，也要指出哪些高风险工具不能仅因“性能最优”而绕过授权。

## 7. 中等难度考试题（含解析）

1. **题：题设 80% 工作可并行，4 个单元，Amdahl 理论加速比？** 解：S=1/(0.2+0.8/4)=2.5 倍。 **检验：**明确单位和数学条件，计算结果只对题设成立。
2. **题：两条独立分支耗时 3s 与 5s，真正并行且无开销，汇合最短要多久？** 解：由较慢分支决定，max(3,5)=5 秒，而不是 8 秒。 **检验：**需要描述边界、瓶颈或反例，不能把单一指标误当作完整系统质量。
