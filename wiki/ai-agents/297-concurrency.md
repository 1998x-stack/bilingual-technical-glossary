# Concurrency（并发）

> AI Agents · 专题：工程化、成本与可观测性 · 执行容量、任务调度与资源治理

## 1. 核心定义

**Concurrency（并发）**：多个任务在重叠时间区间内持续推进的能力或状态；任务可以交替执行、等待 I/O，也可以部分真正并行。对 Agent 来说同时处理会话、工具调用和工作流分支属于并发，但不必意味着多个 CPU 核同时计算。

**适用边界：**Agent 的任务可能包含模型推理、远程工具、等待人工和不可逆业务写入，因此性能指标需写明测量对象、成功判定、时间周期及硬件/服务配额。算法的理想公式不自动等于实测性能；其他系统的吞吐与延迟数据不能不加条件地移植到 Agent 环境。

## 2. 形象理解

**类比：**一个服务员在顾客点餐和等菜期间穿插服务多桌。

**类比的局限：**如果只有一名服务员，点单动作并非同时发生；任务交错不等于同一时刻并行计算。 真实工作流的重试、排队、限流与成本上限使“更多资源=更快”经常不成立，需建立可验证的性能假设。

## 3. 技术原理与核心内容

异步事件循环和任务调度可以重叠网络等待；Semaphore 设最大在途调用数，Queue 提供背压，deadline/cancel 必须传播。并发上限根据下游容量、平均耗时、内存和 SLO 评估；不受控 fan-out 可能在重试时放大负载。

**执行链与负载模型。**用户任务进入运行时，经队列/调度器、模型和工具调用、状态提交、验收。每一级都有容量、等待时间和失败状态。测量时区分到达、尝试、完成与成功完成的计数；应明确跨服务重试是否被重复统计。对于外部写入，必须依据真实后置状态与幂等键判定，不能只信任模型自然语言。

**测量与调优步骤。**先确定容量瓶颈，再选择控制入口流量、排队深度、fan-out 数或执行单元；对共享资源使用原子计数或一致性契约，防止各子 Agent 独立判断额度造成系统性超支。面向用户的 SLO 和真实后置状态应优先于模型自报成功。

## 4. 工程实践与设计权衡

**工程案例：**研究 Agent 为 40 篇文档同时调用摘要模型，下游只允许 8 个在途调用。运行时使用 semaphore=8 并分批调度，避免 429 与成本预算竞态。

**工程边界与验证。**通过受控压测改变任务到达率、并发/并行度、工具超时与下游限额，采集队列深度、吞吐、P95/P99、429/503 和实际业务完成率。观察瓶颈由 CPU、I/O、远程模型、数据库或工具配额中哪一部分决定。加载测试需避免真实费用或客户副作用，并把所有数值示例标为教学假设；必须设置真实成本预算与停机条件。

**权衡。**增加并行度会引入同步和共享瓶颈；过于激进的限流可能压低吞吐，而过于宽松则可能引起尾延迟爆炸。应综合错误预算、成本、用户体验和公平性选择策略。未知状态写入不能因为重试而重复触发付款或发信。

## 5. 关联知识与易混辨析

Concurrency 与 Parallelism：前者是时间段重叠，后者是在同一时刻有实际计算同时运行。与 Throughput：并发提高可能让完成率升高，也可能只提高排队。

评审设计时先列清楚测量单位：tasks/s、requests/s、tokens/s、在途数、任务时延、费用与配额是不同的量。还要区分逻辑任务与单次 attempt，避免将重试造成的请求量增长解释成真正业务产能增长。

## 6. 中等难度面试题（含参考答案）

1. **问：为什么 I/O 密集 Agent 适合 asyncio，但并不代表所有工作都加速？** 答：事件循环可在等待网络时切换，但 CPU 密集计算仍可能阻塞，需要线程或进程等不同策略。
2. **问：如何给多 Agent 扇出设置安全并发控制？** 答：按共享资源设置 semaphore 和全局预算，限制队列长度与递归分支，取消要同步传播。

答题应说明假设、适用场景和实际验证指标；既能解释算法机制，也要指出哪些高风险工具不能仅因“性能最优”而绕过授权。

## 7. 中等难度考试题（含解析）

1. **题：24 次 API 调用，每批最多并发 6 次且每批均耗时 2s，理想总时间？** 解：24/6=4 批，4×2=8 秒；假设每批同步完成。 **检验：**明确单位和数学条件，计算结果只对题设成立。
2. **题：任务数 20、并发上限 5、各任务执行 1s、无开销，最短完成时间？** 解：ceil(20/5)×1=4 秒；只在任务可并发且无额外瓶颈下成立。 **检验：**需要描述边界、瓶颈或反例，不能把单一指标误当作完整系统质量。
