# Action Plan（行动计划）

> 适用领域：AI Agents · 专题：任务规划与决策 · 相关理论与具体产品能力应依据所引来源和版本区分

## 1. 核心定义

**Action Plan（行动计划）**：Action Plan（行动计划）把高层目标转成可执行动作清单，列出每步的执行者、工具、参数、前置条件、依赖、验证方式与异常回退。与仅有阶段标题的计划相比，它能够直接交给受控执行器调度。

**适用边界：**“可执行”仍需在运行时检查身份权限及当下环境；计划中的授权声明不能替代后台强制校验。

## 2. 形象理解

像烘焙食谱的操作步骤：每步规定温度、时间、材料和完成判断。

**类比的局限：**食谱不会消除烤箱故障，执行前仍需确认材料和设备条件。

## 3. 技术原理与核心内容

每步可建模为 `{id, tool, args, pre, dependencies, timeout, verify, rollback_or_compensate}`。运行器仅在 `pre=true` 且依赖满足时执行，并把结果记入审计；写入使用幂等键，遇到不可逆操作需人工确认。执行过程中动作计划版本化，使修改后的步骤不误用旧参数。

## 4. 工程实践与设计权衡

**工程案例：**客户退款流程：查订单→验证退货资格→核算金额→审批→发送退款→查询交易状态。最后一步必须验证支付服务 ID；若 API 超时不能直接重发退款。

**失败模式与验证：**缺少结果验证、错误的时区或货币单位、计划版本混用都可导致事故。优先在沙箱运行 dry-run 与失败注入，比较计划成功率与实际完成率。

## 5. 关联知识与易混辨析

Action Plan 关注低层工具动作序列；High-level Plan 关注阶段和业务交付；Policy 是根据当前状态选择下一动作的规则，可以动态生成或改变行动计划。

## 6. 中等难度面试题（含参考答案）

1. **问：生产 Agent 的行动计划为何应包含失败分支？** 答：外部接口可能超时或部分执行；没有重试、补偿或人工交接语义会导致重复写入、孤儿状态及错误完成声明。
2. **问：怎样处理执行前参数与当前业务状态不一致？** 答：在执行时重新验证 precondition 与资源版本，如库存变了需重新计算或走审批，不得使用过时参数盲写。

## 7. 中等难度考试题（含解析）

1. **题：执行 A 用 3 s，B 在 A 后 5 s，C 与 B 独立但也在 A 后 4 s，最后 D 依赖 B/C 用 2 s。理论最短时间？** 解：A 3+max(B 5,C 4)+D 2=10 s；依赖图比固定列表更能暴露并行性。
2. **题：计划写 `delete(file)` 但只有读权限，执行器可以先删后提示用户吗？** 解：不可以；执行前应验证授权并停止/请求合法审批；计划文本不能赋予实际权限。
