# Scenario-based Evaluation（基于场景的评测）

> AI Agents · 专题：评测体系与常见基准 · 环境、数据版本和授权范围均为评测前提

## 1. 核心定义

**Scenario-based Evaluation（基于场景的评测）**：Scenario-based Evaluation（基于场景的评测）围绕具体用户情境、环境状态、工具可用性、权限和业务验收设计任务，检查 Agent 在完整约束条件下能否完成目标。与脱离背景的抽象问答相比，它更强调真实决策与状态变化。

**适用边界：**单一故事场景无法代表生产分布。场景必须包括正常流程、权限不足、服务错误和用户改变目标等分支；成功判据应尽可能通过外部事实和可观察行为验证，避免让模型凭说法自评。

## 2. 形象理解

像消防演练不只问‘发生火灾怎么办’，而是在断电、门禁、烟雾等具体条件下测试实际协作能力。

**类比的局限：**演练环境相对可控，真实火情还可能有未覆盖的变量，需要定期更新风险模型。

## 3. 技术原理与核心内容

ScenarioSpec={persona,goal,initial_world,authorized_actions,injectable_faults,max_steps,budget,oracle}。搭建隔离工具环境，给定不同初始数据/失败注入，如数据库过期记录、模拟 429、审批拒绝和双重请求。记录结果成功率、过程越权、轨迹长度、p95 latency 和资源成本；每个场景的评测器依据真实文件/事务状态，不接受模型‘已完成’字样。采用不同种子和难度，按类别比较，而不只报告单个总分。

## 4. 工程实践与设计权衡

**工程案例：**旅行 Agent 的场景：用户需预订高铁和酒店，但其中一家酒店价格突变、火车无票、用户不同意改签。Agent 应在预算内提出真实可选方案，得到批准后提交合法订单，无法完成则返回部分结果与未执行原因。

**失败模式与验证：**场景没有明确用户授权、测试工具总是成功、评分只读最终文本、无法从失败样例定位具体断点。做多角色模拟、故障注入、主观用户满意度与外部客观 oracle 的交叉检验。

## 5. 关联知识与易混辨析

Scenario-based Evaluation 以场景为设计单位；Benchmark 可以包含场景；Eval Set 是具体样例；Trajectory Evaluation 则在单场景内评分行动序列。

## 6. 中等难度面试题（含参考答案）

1. **问：为什么场景评测需要初始世界状态快照？** 答：相同请求在不同资源版本、库存和权限下预期结果不同，缺环境快照无法公平验收或复现。
2. **问：为什么必须测试用户拒绝某种替代方案？** 答：合法 Agent 必须遵循用户意图，不能只为提高成功率擅自支付或改签。

## 7. 中等难度考试题（含解析）

1. **题：场景集 60 例，按正常/权限/故障分成 30、20、10，故障场景占比？** 解：10/60≈16.7%。
2. **题：同一场景 5 次运行成功 3 次，单次成功率的经验估计？** 解：3/5=60%，样本少、应报告不确定性。
