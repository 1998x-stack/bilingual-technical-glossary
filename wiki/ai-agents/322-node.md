# Node（节点）

> AI Agents · 专题：开发实践与生态术语 · 编排、输入构造与运行配置

## 1. 核心定义

**Node（节点）**：节点是编排图中可识别的执行单元，通常接收当前状态/输入并产生状态更新、工具动作或路由决策。节点不是一定等于一个 Agent，也可能是普通函数、检索、人工审批或校验步骤。

**适用范围：**通用概念与具体框架的 API 有区别。特别是 LangGraph 的 Graph API、Python 变量接口和具体 Prompt Template 运行库各自拥有版本与实现约束；不能把某个示例的调度行为当作所有 Agent 的默认能力。

## 2. 形象理解

**类比：**像生产线上的工位：某工位只负责检测质量，另一个负责封装产品，每个工位有明确输入与输出。

**类比的局限：**类比中的顺序和约束不代表真实网络、任务调度与业务权限。Agent 可能跨服务并行、因重试重复运行或在调用后才发现状态未知，所以仍需真实状态模型及明确终止条件。

## 3. 技术原理与核心内容

LangGraph StateGraph 节点通常遵循 `State -> Partial<State>`，框架根据声明的状态模式和 reducer 合并更新。节点最好保持单一职责，并为外部写入定义重试、幂等与补偿契约。节点可有超时、重试或缓存策略，具体依框架版本；相同节点被循环访问并非自动 exactly-once。

**安全与状态前提。**Agent 的模型推断、工具 API 调用和最终业务提交是三个不同事件。无论图如何路由、模板如何格式化，所有高影响写入均需要可信执行器的授权、输入校验、幂等处理和权威后置状态复核；外部文档和工具输出必须保持低信任，不能把引导文字升级成用户权限。真实生产配置与秘密不可出现在知识库、Prompt 或原始日志里。

**设计视角。**首先定义输入数据与状态 schema、允许的后继路径、可观察事件和完成条件，再将复用模块封装为可独立测试的步骤。对动态依赖使用预算和截止时间，对不可信数据明确边界，对参数版本变更设回归用例。

## 4. 工程实践与设计权衡

**工程实例：**发票 Agent 将 OCR 解析、税率校验、用户审批和最终入账拆成节点。重启时允许重做只读 OCR，入账节点则通过操作 ID、真实 ledger 和授权验证防重复。

**测试与可观测性。**为同一个可重复任务建立基线，记录任务/跨度 ID、版本、分支选择、输入数据来源、成功验收条件与完成时延。在隔离环境注入超时、缺字段、并行写同一状态、循环次数超限、取消/恢复和恶意检索内容，检查错误分支与副作用控制。运行时不只判断模型自报“成功”，还要核实工具结果、业务数据库/账本与权限审计。

**工程权衡。**抽象化可以提高复用与可读性，却可能隐藏框架默认的并发/重试及额外 token 成本；限制过严会牺牲灵活性，限制过宽则放大提示注入和重复副作用风险。重要策略需要日志可追踪、配置可复核、失败可回退。

## 5. 关联知识与易混辨析

Node 是图上的计算/控制实体；Tool 是可供调用的外部能力；Agent 是具模型决策能力的运行单元。一个节点可以调用工具或 Agent，不能把这些抽象相互等价。

跨术语评审应分别回答：这是执行节点、控制关系、生成输入的模板，还是进程配置？它对用户成功率、权限边界和数据来源有什么影响？名称相似并不意味着相同的运行时保证。

## 6. 中等难度面试题（含参考答案）

1. **问：为何要拆分一个同时检索、审批和付款的巨大节点？** 答：单一职责有利于权限隔离、重试策略、观测、单元测试与局部恢复；写入节点尤其要与审批边界分开。
2. **问：重启工作流后，什么节点适合自动重放，什么节点必须额外保护？** 答：只读且确定性步骤通常较容易重放；外部发送或付款节点需持久化操作 ID、幂等与后置状态核对。

优秀回答应该说明真实系统的约束、边界故障以及如何通过测试验证，而非只复述单个 API 名称。

## 7. 中等难度考试题（含解析）

1. **题：5 个节点顺序执行，分别用时 1、2、3、2、2 秒，无并发，理想时长？** 解：1+2+3+2+2=10 秒。 **注意：**数值和前提仅来自题设，不是生产实测。
2. **题：并行两个节点都写 `count=1`，若框架默认覆盖，是否得到 `count=2`？** 解：不保证。必须显式设计加和 reducer/原子聚合及避免重复更新，不能把覆盖理解为累加。 **注意：**明确执行路径或参数范围，不能把未执行的分支、额外权限或隐含转换计入结果。
