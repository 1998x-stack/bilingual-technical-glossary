# Rate Limiting（速率限制）

> AI Agents · 专题：工程化、成本与可观测性 · 执行容量、任务调度与资源治理

## 1. 核心定义

**Rate Limiting（速率限制）**：按单位时间约束用户、租户或服务可发起的调用数/资源消耗，是防止下游过载、滥用或意外成本激增的入口控制。速率限制可以拒绝、排队、延迟、降级，具体行为依策略而定。

**适用边界：**Agent 的任务可能包含模型推理、远程工具、等待人工和不可逆业务写入，因此性能指标需写明测量对象、成功判定、时间周期及硬件/服务配额。算法的理想公式不自动等于实测性能；其他系统的吞吐与延迟数据不能不加条件地移植到 Agent 环境。

## 2. 形象理解

**类比：**入口闸机每分钟允许一定人数进入，并可允许短时间少量突发。

**类比的局限：**流量限制不能确保所有进入者都得到服务；昂贵长任务还可能占满并发资源。 真实工作流的重试、排队、限流与成本上限使“更多资源=更快”经常不成立，需建立可验证的性能假设。

## 3. 技术原理与核心内容

Token Bucket 以速率 r 补充令牌且桶容量 B 限突发；固定窗口容易在边界突发，滑动窗口更均匀但更贵。拒绝通常返回 HTTP 429，并可能带 Retry-After；还需限在途并发、成本和请求大小。多实例必须明确计数器共享/最终一致性。

**执行链与负载模型。**用户任务进入运行时，经队列/调度器、模型和工具调用、状态提交、验收。每一级都有容量、等待时间和失败状态。测量时区分到达、尝试、完成与成功完成的计数；应明确跨服务重试是否被重复统计。对于外部写入，必须依据真实后置状态与幂等键判定，不能只信任模型自然语言。

**测量与调优步骤。**先确定容量瓶颈，再选择控制入口流量、排队深度、fan-out 数或执行单元；对共享资源使用原子计数或一致性契约，防止各子 Agent 独立判断额度造成系统性超支。面向用户的 SLO 和真实后置状态应优先于模型自报成功。

## 4. 工程实践与设计权衡

**工程案例：**Agent 一秒发出 100 次工具调用，下游允许 20 req/s；入口早拒绝或排队并反馈退避。模型不应每次 429 都立即无限重试，需抖动、幂等与共享预算。

**工程边界与验证。**通过受控压测改变任务到达率、并发/并行度、工具超时与下游限额，采集队列深度、吞吐、P95/P99、429/503 和实际业务完成率。观察瓶颈由 CPU、I/O、远程模型、数据库或工具配额中哪一部分决定。加载测试需避免真实费用或客户副作用，并把所有数值示例标为教学假设；必须设置真实成本预算与停机条件。

**权衡。**增加并行度会引入同步和共享瓶颈；过于激进的限流可能压低吞吐，而过于宽松则可能引起尾延迟爆炸。应综合错误预算、成本、用户体验和公平性选择策略。未知状态写入不能因为重试而重复触发付款或发信。

## 5. 关联知识与易混辨析

Rate Limiting 是单位时间速度限制；Quota 是长期总额度；Concurrency Limit 是在途任务数限制。只设一个不会解决另外两个维度。

评审设计时先列清楚测量单位：tasks/s、requests/s、tokens/s、在途数、任务时延、费用与配额是不同的量。还要区分逻辑任务与单次 attempt，避免将重试造成的请求量增长解释成真正业务产能增长。

## 6. 中等难度面试题（含参考答案）

1. **问：Token Bucket 和 Fixed Window 在突发流量下的差别？** 答：令牌桶允许容量 B 的有限突发并持续补充，固定窗口边界可双倍集中；选择取决于下游容忍度。
2. **问：收到 429 后 Agent 怎样重试才不形成重试风暴？** 答：遵循 Retry-After，指数退避加抖动，并设置最多尝试、截止时间与幂等键。

答题应说明假设、适用场景和实际验证指标；既能解释算法机制，也要指出哪些高风险工具不能仅因“性能最优”而绕过授权。

## 7. 中等难度考试题（含解析）

1. **题：令牌桶容量 10，现有 2 个令牌，补充速率 3/s，静止 2s 后有多少？** 解：min(10,2+3×2)=8 个令牌。 **检验：**明确单位和数学条件，计算结果只对题设成立。
2. **题：限速 10 req/s 但每请求占用 30s，为什么还需要额外控制？** 解：在途约可累积 300 个（假设持续稳定接受且无其他瓶颈）；可能耗尽内存或外部连接，需并发/队列上限。 **检验：**需要描述边界、瓶颈或反例，不能把单一指标误当作完整系统质量。
